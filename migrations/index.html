    Database Migrations

    Overview

    This project uses Alembic, a database migration tool for SQLAlchemy, to manage database schema changes in a controlled and versioned manner. Migrations allow you to evolve your database schema over time while preserving existing data.

    Key benefits of using Alembic:

    • Track database schema changes in version control
    • Easily upgrade or downgrade your database to specific versions
    • Automatically generate migration scripts based on model changes
    • Apply migrations consistently across different environments

    Directory Structure

    migrations/
├── env.py                # Environment configuration for Alembic
├── README                # Documentation
├── script.py.mako        # Template for generating migration scripts
└── versions/             # Directory containing all migration versions
    ├── 2025_01_16_0414_17f9dafacfb9_add_user_table.py
    └── 2025_01_18_0629_3f15bec04ed2_add_posts_table.py

    Configuration Files

    alembic.ini

    This is the main configuration file for Alembic. Key settings include:

    • script_location: Path to migration scripts (migrations)
    • file_template: Format for naming migration files (customized to include date and time)
    • version_path_separator: Used when specifying multiple version paths
    • Logging configuration settings

    env.py

    This script configures how Alembic interacts with your application:

    • Connects Alembic to your SQLAlchemy models (Base.metadata)
    • Configures database connection settings from your application config
    • Defines migration execution methods for both online and offline modes
    • Sets up proper Python path to access your application modules

    Migration Naming Convention

    Our migrations follow this naming pattern: 

    YYYY_MM_DD_HHMM_<revision_id>_<slug>.py

    For example: 

    2025_01_16_0414_17f9dafacfb9_add_user_table.py

    Where:

    • 2025_01_16: Year, month, day (January 16, 2025)
    • 0414: Time (4:14 AM)
    • 17f9dafacfb9: Unique revision ID generated by Alembic
    • add_user_table: Descriptive slug describing the migration's purpose

    This naming convention allows for:

    • Easy chronological sorting of migrations
    • Quick identification of when a migration was created
    • Clear understanding of what each migration does

    Working with Migrations

    Creating a New Migration

    To generate a new migration script:

    make generate-migration

    You'll be prompted to enter a migration message (e.g., "add_user_profile_fields"). This command runs alembic revision --autogenerate -m "your_message", which:

    1. Examines the differences between your current models and database
    2. Creates a new migration script in the versions/ directory
    3. Adds both upgrade() and downgrade() functions to the script
    Tip

    Always review auto-generated migrations before applying them. Alembic may not detect all changes correctly (especially complex ones like renamed columns).

    Example migration script:

    2025_01_18_0629_3f15bec04ed2_add_posts_table.py
    def upgrade():
    # Add new posts table
    op.create_table(
        'posts',
        sa.Column('id', sa.Integer(), nullable=False),
        sa.Column('title', sa.String(length=100), nullable=False),
        sa.Column('content', sa.Text(), nullable=True),
        sa.Column('user_id', sa.Integer(), nullable=False),
        sa.ForeignKeyConstraint(['user_id'], ['users.id']),
        sa.PrimaryKeyConstraint('id')
    )

def downgrade():
    # Drop the posts table
    op.drop_table('posts')

    Applying Migrations

    To apply all pending migrations up to the latest version:

    make migrate

    This runs alembic upgrade head, which:

    • Identifies which migrations haven't been applied
    • Runs each migration's upgrade() function in the correct order
    • Updates Alembic's version tracking table in your database

    Rolling Back Migrations

    To roll back the most recent migration:

    make rollback

    This executes alembic downgrade -1, which:

    • Runs the downgrade() function of the most recent migration
    • Updates Alembic's version tracking to reflect the change

    Complete Database Reset

    To roll back all migrations and start fresh:

    make reset-database

    This runs alembic downgrade base, which:

    • Sequentially executes all downgrade() functions in reverse order
    • Returns the database to its initial state before any migrations were applied

    Best Practices

    1. Descriptive migration names 📝

    2. Use clear, concise descriptions in migration messages

    3. Example: "add_user_table" instead of "update1"

    4. Test migrations before deployment 🧪

    5. Verify both upgrade() and downgrade() functions work correctly

    6. Test on a copy of production data when possible

    7. One logical change per migration 🧩

    8. Keep migrations focused on a single purpose

    9. Easier to understand, test, and troubleshoot

    10. Include both up and down migrations ⬆️⬇️

    11. Always implement the downgrade() function

    12. Ensures you can roll back changes if needed

    13. Data migrations 📊

    14. When changing column types or structure, don't forget to migrate existing data

    15. May require custom SQL or Python code in migrations

    16. Review auto-generated migrations 👀

    17. Auto-generation is convenient but not perfect

    18. Always check for correctness before applying

    Common Commands

    Command Description
    alembic init migrations Initialize a new Alembic environment
    alembic revision --autogenerate -m "message" Generate a new migration automatically
    alembic revision -m "message" Create a blank migration manually
    alembic upgrade head Apply all pending migrations
    alembic upgrade +1 Apply the next pending migration
    alembic downgrade -1 Roll back the most recent migration
    alembic downgrade base Roll back all migrations
    alembic current Show current migration version
    alembic history Show migration history

    Troubleshooting

    Missing Tables

    If Alembic complains about missing tables when generating migrations:

    • Ensure your models are properly imported in env.py
    • Verify that target_metadata is correctly set to your Base.metadata

    Autogenerate Not Detecting Changes

    Alembic might not detect certain changes:

    • Constraints and indexes may need manual specification
    • Changes to server defaults might not be detected
    • Custom column types might require special handling

    Migration Order Conflicts

    If you encounter order conflicts:

    • Use alembic merge to combine conflicting migrations
    • Consider using branches for complex concurrent development
